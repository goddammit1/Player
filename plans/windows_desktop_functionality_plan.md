# План реализации функционала Windows desktop

## 1. Цель

Довести уже реализованный desktop frontend до полноценного сценария прослушивания музыки на Windows, не создавая новые страницы и не изменяя поведение мобильной версии.

Основной пользовательский поток:

1. Пользователь вводит запрос в верхней строке поиска.
2. Приложение показывает результаты и позволяет выбрать трек.
3. Выбранный трек запускается, а результаты формируют очередь.
4. Пользователь управляет воспроизведением из нижней панели.
5. Очередь и текущий трек доступны в правой панели или в компактном представлении при узком окне.
6. Состояние воспроизведения корректно переживает перезапуск приложения.

## 2. Границы работ

### Входит в текущий этап

- Только Windows desktop.
- Текущая оболочка из [`desktop_shell.dart`](../lib/ui/desktop/desktop_shell.dart).
- Верхний поиск из [`desktop_top_bar.dart`](../lib/ui/desktop/desktop_top_bar.dart).
- Нижняя панель из [`desktop_player_bar.dart`](../lib/ui/desktop/desktop_player_bar.dart).
- Правая панель Queue/Track из [`queue_panel.dart`](../lib/ui/desktop/queue_panel.dart).
- Существующая главная страница плейлистов из [`desktop_home_page.dart`](../lib/ui/desktop/desktop_home_page.dart).
- Windows-реализация воспроизведения из [`player_service_desktop.dart`](../lib/core/platform/player_service_desktop.dart).
- Подключение существующей общей логики поиска, источников, плейлистов, истории, кэша и настроек там, где она нужна текущему desktop frontend.
- Мышь, клавиатура, изменение размера окна, состояния загрузки и ошибки.
- Автоматические тесты и ручная приемка Windows-сборки.

### Не входит в текущий этап

- Новые desktop-страницы.
- Полная переработка History, Playlist, Settings и их дочерних страниц под отдельный Windows-дизайн.
- Обязательная поддержка Linux и macOS.
- Изменение мобильной компоновки, мобильной навигации, жестов или фонового сервиса воспроизведения.
- Добавление новых музыкальных источников.
- Эквалайзер и другая новая DSP-функциональность.

## 3. Правила изоляции мобильной версии

1. Desktop UI изменяется преимущественно внутри [`lib/ui/desktop`](../lib/ui/desktop).
2. Windows-специфичная логика плеера изменяется внутри [`player_service_desktop.dart`](../lib/core/platform/player_service_desktop.dart).
3. Общий контракт [`PlayerServiceInterface`](../lib/core/player_service_interface.dart:7) расширяется только при необходимости и только обратно совместимым способом.
4. Мобильная реализация в [`player_service.dart`](../lib/core/player_service.dart) не должна менять поведение из-за desktop-задач.
5. Ветвление платформ сохраняется в [`PlayerServiceFactory.create()`](../lib/core/platform/player_service_factory.dart:28) и [`isDesktop`](../lib/ui/desktop/desktop_layout.dart:11).
6. После каждого этапа выполняются общие тесты, чтобы изменения Windows не сломали Android/iOS.

## 4. Результаты аудита текущего frontend

### Уже реализовано

- Windows выбирает отдельный корень приложения через [`PlayerApp.build()`](../lib/main.dart:264).
- Нижняя панель вынесена поверх навигации через [`DesktopFrame`](../lib/ui/desktop/desktop_frame.dart:25).
- Desktop использует отдельный плеер через [`DesktopPlayerService`](../lib/core/platform/player_service_desktop.dart:23).
- Главная содержит сетку плейлистов, создание, переименование, удаление и перестановку.
- Верхняя строка выполняет поиск и показывает результаты в центральной области.
- Нижняя панель уже содержит визуальные элементы play/pause, previous/next, shuffle, repeat, seek, volume и add-to-playlist.
- Правая колонка отображает очередь и позволяет перейти к элементу.
- Существующие Playlist, History и Settings могут открываться внутри текущей оболочки или поверх нее.

### Обнаруженные функциональные разрывы

1. Кнопка Queue в [`_ControlsAndTimeline.build()`](../lib/ui/desktop/desktop_player_bar.dart:178) имеет пустой обработчик.
2. В [`_QueuePanelState`](../lib/ui/desktop/queue_panel.dart:25) переключается вкладка Queue/Track, но тело панели всегда строит один и тот же список.
3. При ширине окна меньше 960 пикселей [`DesktopShell`](../lib/ui/desktop/desktop_shell.dart:89) полностью скрывает правую панель, а альтернативного доступа к очереди нет.
4. Текущая очередь не предоставляет desktop-действия удаления, очистки и drag-and-drop reorder, хотя сервис уже содержит соответствующие операции.
5. Метаданные источника и качества в [`_TrackInfo.build()`](../lib/ui/desktop/desktop_player_bar.dart:107) подменяются фиктивными значениями, если данные отсутствуют.
6. Ошибки воспроизведения в сервисе в основном уходят в лог и недостаточно отражаются в UI.
7. Критические desktop-сценарии с клавиатурой еще не реализованы.
8. Встроенные общие страницы местами зависят от long-press и swipe, которые неудобны или неочевидны на Windows.
9. Тесты Queue/Track и нижней панели содержат ожидания, которые не совпадают с текущей реализацией, поэтому перед разработкой нужен baseline-аудит.

## 5. Архитектурный подход

### UI

- [`DesktopShell`](../lib/ui/desktop/desktop_shell.dart) остается владельцем навигации, центральной области и видимости правой панели.
- [`DesktopFrame`](../lib/ui/desktop/desktop_frame.dart) остается владельцем постоянно видимой нижней панели.
- Для открытия очереди из нижней панели вводится небольшой desktop-контроллер состояния, доступный через Riverpod.
- На широком окне контроллер управляет правой колонкой и выбранной вкладкой.
- На узком окне тот же контроллер открывает существующее содержимое Queue/Track как overlay или side panel, а не как новую страницу.
- Состояния Queue и Track должны использовать один источник данных — текущий [`PlayerServiceInterface`](../lib/core/player_service_interface.dart:7).

### Плеер

- [`DesktopPlayerService`](../lib/core/platform/player_service_desktop.dart:23) остается единственным владельцем очереди, текущего индекса, переходов между треками, repeat/shuffle, восстановления сессии и обработки ошибок.
- UI не должен вручную вычислять следующий индекс или самостоятельно изменять очередь в обход сервиса.
- Все длительные операции должны публиковать понятное состояние: loading, buffering, ready, completed или error.
- Ошибка одного трека не должна навсегда блокировать очередь.

### Состояние и реактивность

- Очередь должна обновлять UI после add, insert, remove, reorder, shuffle и restore.
- Текущий интерфейс предоставляет список через [`PlayerServiceInterface.trackQueue`](../lib/core/player_service_interface.dart:64), но не предоставляет отдельный реактивный поток очереди. На этапе реализации необходимо либо добавить обратно совместимый queue stream, либо создать desktop-адаптер, который гарантированно уведомляет UI после каждой мутации.
- Предпочтительный вариант — добавить в общий контракт поток снимков очереди и реализовать его в обоих сервисах без изменения мобильного поведения.

## 6. План задач

### Этап 1. Baseline после последнего pull

- [ ] Не менять функциональность до получения воспроизводимого baseline.

**Критерий готовности:** существует точный список исходных проблем и понятен набор тестов, который должен стать зеленым.

### Этап 2. Контракт реактивной очереди

- [ ] Определить единый реактивный источник очереди и текущего индекса.
- [ ] Обеспечить уведомление после set, add, insert, remove, reorder, shuffle, clear и restore.
- [ ] Сохранить обратную совместимость существующих вызовов.
- [ ] Реализовать контракт в Windows-плеере.
- [ ] При необходимости реализовать нейтральную совместимую поддержку в мобильном сервисе без изменения UI и поведения.
- [ ] Добавить unit-тесты мутаций очереди.

**Критерий готовности:** Queue UI обновляется без ручного rebuild и всегда совпадает с фактическим состоянием плеера.

### Этап 3. Стабилизация Windows-плеера

- [ ] Проверить запуск очереди с произвольного индекса.

- [ ] Реализовать предсказуемый previous: возврат к началу после заданного порога и переход к предыдущему треку в начале композиции.
- [ ] Реализовать next и завершение последнего трека.
- [ ] Проверить repeat off, all и one.
- [ ] Исправить shuffle так, чтобы текущий трек не терялся и текущий индекс оставался корректным.
- [ ] Проверить seek при известной и неизвестной длительности.
- [ ] Не допускать параллельного запуска устаревшего запроса после быстрого переключения треков.
- [ ] Ограничить автоматический skip при серии ошибок и завершать цикл понятным error-state.
- [ ] Добавить unit-тесты всех переходов состояния.

**Критерий готовности:** базовое воспроизведение и навигация по очереди детерминированы и не зависят от скорости сети.

### Этап 4. Сохранение и восстановление сессии

- [ ] Сохранять очередь, текущий индекс, позицию, play/pause, громкость и repeat mode.

- [ ] Восстанавливать позицию только в допустимом диапазоне длительности.
- [ ] Безопасно обрабатывать удаленные источники, поврежденные записи и отсутствующие локальные файлы.

**Критерий готовности:** после перезапуска пользователь видит прежнюю очередь и позицию, но воспроизведение начинается только по его команде.

## 7. Приоритет реализации

### P0 — обязательный listening MVP

1. Baseline и устранение compile/runtime-блокеров.
2. Реактивная очередь.
3. Надежное воспроизведение и переходы между треками.
4. Полностью рабочая нижняя панель.
5. Реальная Queue-вкладка.
6. Поиск до воспроизведения.
7. Ошибки, retry и skip.
8. Восстановление сессии.
9. Автоматические тесты и Windows release-проверка.

### P1 — завершение текущего frontend

1. Track-вкладка.
2. Очередь в узком окне.
3. Drag-and-drop reorder и контекстные действия.
4. Горячие клавиши.
5. Desktop-альтернативы long-press и swipe на существующих страницах.

### P2 — последующая полировка

1. Дополнительные hover/focus-анимации.
2. Точная настройка breakpoint и размеров.
3. Расширенные системные media key сценарии.
4. Улучшение текстов ошибок и empty-state.

## 8. Definition of Done

Этап считается завершенным, когда одновременно выполнены условия:

- Windows-пользователь может найти трек, запустить его и управлять непрерывным воспроизведением.
- Все видимые кнопки текущего desktop frontend работают или явно disabled.
- Queue и Track имеют различное рабочее содержимое.
- Очередь доступна в широком и узком окне.
- Ошибка трека не блокирует приложение.
- Сессия корректно восстанавливается без autoplay.
- Нет обязательных действий, доступных только через мобильный жест.
- Нижняя панель остается видимой при существующих переходах.
- Desktop-тесты и общий набор тестов проходят.
- Windows release-сборка проверена вручную.
- Мобильная версия не получила визуальных или поведенческих изменений.
