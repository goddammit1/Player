# План исправления Soulseek после диагностики Android-сессии

## 1. Резюме и доказательства

Первая итерация: исправить запуск foreground service и исключить публикацию непроверенного аудиокэша. Восстановление сессии и предупреждения локализации — независимые низкоприоритетные задачи.

Основание: [crash_log_session.txt](../crash_log_session.txt), пользовательские сценарии и статическое изучение текущих исходников. Формат ссылок соответствует [плану интеграции](soulseek_source_integration_plan.md). Команды ниже предназначены для будущего исполнителя: при подготовке документа сборка и тесты не запускались, исходники не изменялись. Совпадение установленного APK с текущей ревизией ещё нужно подтвердить.

**Уточнение:** в текущем [манифесте](../android/app/src/main/AndroidManifest.xml:8) разрешение [`android.permission.FOREGROUND_SERVICE_DATA_SYNC`](../android/app/src/main/AndroidManifest.xml:8) объявлено, но ограничено [`android:maxSdkVersion="33"`](../android/app/src/main/AndroidManifest.xml:8), поэтому не действует на API 34+. Тип сервиса сейчас — [`dataSync|specialUse`](../android/app/src/main/AndroidManifest.xml:59), а не только dataSync. Исправление должно учитывать фактический код, не добавлять дублирующее разрешение.

## 2. Цели и критерии готовности

- [ ] Release APK содержит правильные разрешения/типы FGS; сервис действительно в foreground, девять повторных стартов не вызывают отказов.
- [ ] Неуспех запуска сервиса завершается контролируемо, без сетевой работы под видом успешного FGS и зависших команд.
- [ ] Плеер получает только завершённый проверенный final-файл. Нулевые, неполные, oversized и невалидные файлы не становятся готовым кэшем.
- [ ] Контрольный FLAC воспроизводится до конца, перематывается и повторно открывается из кэша без загрузки.
- [ ] Повреждённый результат инвалидируется; retry ограничен общим бюджетом, ошибочный файл не открывается снова бесконечно.
- [ ] Один ключ — один писатель; все ожидающие получают согласованный результат, старые события не завершают новую попытку.
- [ ] Все пять пользовательских сценариев повторно проверены на установленном приложении; логи, версия APK и ограничения проверки сохранены.
- [ ] SESSION-01 и MONO-01 выполнены отдельно либо явно отложены.

3. Сопоставить запрос трека, ключ кэша, попытку, offset, запись файла, завершение .NET, регистрацию Kotlin, выдачу пути Dart и ошибку Media3. Индекс 0 плеера не считать автоматически индексом пользовательской очереди.

Добавить корреляционную диагностику в [обёртку](../soulseek-wrapper/SoulseekBridge.cs:297), [transfer manager](../android/app/src/main/kotlin/com/player/player/SoulseekTransferManager.kt:242), [cache manager](../android/app/src/main/kotlin/com/player/player/SoulseekCacheManager.kt:132), [источник](../lib/sources/soulseek_source.dart:265) и [плеер](../lib/core/player_service.dart:395). Поля: ключ, поколение попытки, слой/состояние, ожидаемый/согласованный/фактический размер, offset, причина отказа, retry и длительность проверки. Имена редактировать/хешировать.
5. Подготовить контролируемый пир с известным валидным FLAC и негативные фикстуры; публичную сеть не делать зависимостью unit-тестов.

## 4. Этап 1 — FGS permission и запуск сервиса

### Изменения по компонентам

- [AndroidManifest.xml](../android/app/src/main/AndroidManifest.xml:8): убрать ограничение API 33 у разрешения dataSync, сохранить базовое разрешение foreground service. Проверить разрешения для всех реально передаваемых типов.
- [`SoulseekForegroundService.onStartCommand()`](../android/app/src/main/kotlin/com/player/player/SoulseekForegroundService.kt:127): инициализация сети только после успешного foreground; остановка без лишней инициализации.
- [`startForegroundCompat()`](../android/app/src/main/kotlin/com/player/player/SoulseekForegroundService.kt:247): текущий catch логирует ошибку и разрешает продолжение. Заменить на явный результат/контролируемый отказ: остановить сервис, освободить ресурсы, передать ошибку клиенту. Различать permission failure и запрет фонового старта.
- [`SoulseekPlugin.ensureServiceStarted()`](../android/app/src/main/kotlin/com/player/player/SoulseekPlugin.kt:438): идемпотентные start/bind, ограниченное ожидание готовности, завершение pending-команд при отказе. Отправка intent не равна готовности сервиса; исключить шторм повторных стартов.
- [SoulseekNotification.kt](../android/app/src/main/kotlin/com/player/player/SoulseekNotification.kt): канал/уведомление создаются до сети; проверить разрешённые и запрещённые уведомления отдельно.

### Совместимость и приёмка

1. Проверить **release merged manifest**, merger report и итоговый APK, затем debug: разрешение не ограничено API 33, не удалено overlay/библиотекой; маска типов согласована с декларацией. Проверить эффективные min/compile/target SDK в [build.gradle.kts](../android/app/build.gradle.kts:19), не снижать target для обхода требований.
2. API ниже 29 — совместимый вызов без маски; API 29–33 — dataSync; API 34+ — type-specific permissions для каждого типа. FGS permissions не требуют runtime-диалога; разрешение уведомлений не заменяет их.
3. На API 31+ проверить background-start restrictions, запуск из допустимого пользовательского/foreground-контекста, отсутствие автоматического обходного restart-loop.
4. Проверить необходимость specialUse и обоснование для распространения. Не считать его способом обхода ограничений dataSync и не подменять передачу файлов типом mediaPlayback.
5. На API 35+ при соответствующем target проверить лимит фонового dataSync, включая суммарный шестичасовой бюджет за 24 часа, обработку timeout и своевременную остановку. Проверить актуальные требования API 36. FGS не гарантирует бессрочного подключения.
6. Device-кейсы: первый/повторный старт, bind/rebind, закрытие настроек, пересоздание Activity, фон, запрещённые уведомления, завершение процесса и следующий разрешённый запуск. После force-stop самопроизвольный рестарт не требуется.

Выход этапа: фактический foreground подтверждён состоянием ОС; инъекция отказа не оставляет сеть/команды в ложном успешном состоянии. Влияние на остальные симптомы проверяется отдельно.

## 5. Этап 2 — FLAC/cache pipeline

### 5.1. Факты и гипотезы

Слабое место подтверждено кодом, причина конкретного повреждения — нет. |
| Resume мог повторить/пропустить байты или использовать неподходящий остаток. | Проверить [append-поток и offset](../soulseek-wrapper/Soulseek.NET/SoulseekClient.cs:3379), автоматический seek; сравнить хеш чистой загрузки и pause/resume. Не утверждать дефект append/seek без теста. |

### 5.2. Контракт публикации

Порядок: очередь → запись временного файла → закрытие/flush → проверка размера и формата → atomic rename → регистрация проверенного кэша → событие завершения → путь для плеера.

- Временное имя [`<cacheKey>.part`](../soulseek-wrapper/SoulseekBridge.cs:310), финальное [`<cacheKey>.<extension>`](../soulseek-wrapper/SoulseekBridge.cs:311). Оба на одной файловой системе в приватной директории; временный путь никогда не выдаётся плееру.
- Один владелец записи на ключ. Resume разрешён только при совпадении пира, удалённого пути и ожидаемого размера. Проверить одинаковость ключей Kotlin/Dart, включая Unicode.
- Размер обязан совпасть с согласованным ожидаемым размером. Превышение — ошибка, равенство — необходимое, но недостаточное условие. Счётчик сегмента не путать с полной длиной с учётом offset.
- EOF не доказывает полноту: соединение могло оборваться. Нужны успешное протокольное завершение, согласованная длина и отсутствие обрезанных структур контейнера. При неизвестном размере получить подтверждённый размер от протокола либо не публиковать; текущий [Dart-контракт](../lib/sources/soulseek_source.dart:281) требует положительный размер.
- FLAC: сигнатура fLaC, STREAMINFO, границы/последний блок метаданных, допустимый sync/header первого фрейма. Явно определить поддержку ID3-префикса и Ogg FLAC по возможностям декодера, не отвергать валидные файлы случайной эвристикой.
- Сигнатура и первый фрейм не доказывают целостность всего аудио. Диагностика включает полное декодирование до EOF; глубину production-валидации выбрать и измерить, описать пределы гарантии. При доступном эталоне сравнить хеш, при наличии корректного FLAC MD5 проверить его; локальный SHA-256 без эталона не доказывает совпадение с оригиналом.
- Остальные форматы проверять по собственным контейнерам, а не FLAC-правилам. HTML/JSON/ошибочный payload отклонять до публикации; не полагаться только на расширение или первый символ.

### 5.3. .NET: запись и атомарное завершение

Компоненты: [`DownloadToFileCoreAsync()`](../soulseek-wrapper/SoulseekBridge.cs:297), [`AtomicRename()`](../soulseek-wrapper/SoulseekBridge.cs:772), [SoulseekDtos.cs](../soulseek-wrapper/SoulseekDtos.cs), [SoulseekClient.cs](../soulseek-wrapper/Soulseek.NET/SoulseekClient.cs:3379).

1. Объединить обычное завершение и ветвь уже полного частичного файла через один валидатор. Убрать успех при oversized; нулевой остаток начать заново, заведомо битый не использовать для resume.
2. Проверить гарантии закрытия/dispose/flush потока до проверки и rename. После отмены дождаться прекращения писателя перед удалением/повторным открытием. Оценить необходимость durable flush для сценария потери питания.
3. Вынести валидатор в тестируемую логику с ограниченной памятью и дисковым чтением вне UI. Структурировать ошибки: неполная передача, размер, формат, FLAC, диск, публикация. Согласовать поля с [Kotlin-событиями](../android/app/src/main/kotlin/com/player/player/SoulseekEvent.kt) и [Dart-моделями](../lib/sources/soulseek_models.dart).
4. Текущий helper удаляет final перед перемещением: это не атомарная замена всей операции. Выбрать подтверждённый для .NET Android способ атомарной замены на одной ФС, без скрытого copy/delete fallback. При наличии валидного final предпочесть reuse под блокировкой. Ошибка rename не означает успех и не должна уничтожать предыдущий валидный файл.
5. Различать атомарность видимости и устойчивость к потере питания. Rename и SQLite не образуют общую транзакцию: сбой между ними восстанавливается reconciliation.
6. Включённую Soulseek.NET менять только после доказательства дефекта её потокового/протокольного контракта, сначала защитить границу обёртки.

### 5.4. Kotlin: готовность кэша, БД и очистка

Компоненты: [SoulseekTransferManager.kt](../android/app/src/main/kotlin/com/player/player/SoulseekTransferManager.kt:430), [SoulseekCacheManager.kt](../android/app/src/main/kotlin/com/player/player/SoulseekCacheManager.kt:75), [SoulseekDatabase.kt](../android/app/src/main/kotlin/com/player/player/SoulseekDatabase.kt), [SoulseekPlugin.kt](../android/app/src/main/kotlin/com/player/player/SoulseekPlugin.kt:346).

1. Сейчас завершение выставляется до регистрации, её неуспех не блокирует событие. Перестроить: результат .NET → проверка канонического пути внутри кэша/ключа/расширения/длины/валидации → запись БД → завершение. Не доверять произвольному пути bridge и старому поколению попытки.
2. На cache hit проверять не только наличие/ненулевую длину и флаг готовности, но ожидаемую длину, идентичность и версию валидации. При необходимости добавить поля безопасной миграцией. Старые записи перепроверять лениво перед использованием или контролируемо на старте, не сносить весь кэш.
3. Reconciliation: нет final → удалить зависшую запись; final без записи → проверить и зарегистрировать либо удалить/карантинировать; частичный файл → только resume; неправильная длина → invalidation. Наличие файла само по себе не означает готовность.
4. Очистку согласовать с активным писателем: отменить/дождаться, инвалидировать БД/Dart-индекс, удалить final и остаток, обработать отказ удаления. Учесть orphan-final без строки БД. Невалидность важнее pin, но намерение пользователя закрепить трек сохранить для новой загрузки.
5. Защитить публикуемый и воспроизводимый файл от LRU временной lease/reference protection отдельно от пользовательского pin. [`completeTransfer()`](../android/app/src/main/kotlin/com/player/player/SoulseekCacheManager.kt:132) сразу вызывает cleanup — проверить, что она не удаляет только что выданный путь.

### 5.5. Retry/backoff и concurrency/dedupe

Основная точка — [цикл трансфера](../android/app/src/main/kotlin/com/player/player/SoulseekTransferManager.kt:242). Сейчас [`handleTransferFailure()`](../android/app/src/main/kotlin/com/player/player/SoulseekTransferManager.kt:348) выставляет terminal failure, после чего цикл выходит: константы retry не доказывают работающих повторов.

- Kotlin — единственный владелец сетевого retry. Промежуточное ожидание retry не должно выглядеть для Dart окончательным failure. Финальный отказ — после бюджета или неретрайной причины.
- Начальная политика: максимум три сетевые попытки всего; exponential backoff от 2 секунд с jitter и пределом 30 секунд. Проверить точный счётчик/задержки виртуальными часами, не удерживать сетевой слот во время ожидания.
- Сетевой обрыв допускает проверенный resume. Повреждённый формат — максимум одна чистая перезагрузка в общем бюджете, без продолжения битого остатка. Повтор идентичного невалидного результата у того же пира — окончательный отказ. Другой пир не подставляется молча по названию.
- Permission/параметры/неподдерживаемый формат/нехватка места/отмена пользователя не запускают слепой сетевой retry.
- Playback recovery не перемножает бюджет с transfer retry; повтор после ошибки декодера учитывается в общей операции.
- Атомарно проверять и регистрировать ключ. Concurrent map не делает check-then-put атомарным. Одна блокировка/владелец на ключ охватывает start/resume/cancel/remove/publish.
- Ввести поколение попытки между .NET/Kotlin/Dart: детерминированный ID загрузки не отличает старое событие от нового старта. Поздний callback/cleanup не меняет новую попытку.
- Один файл — общий результат для всех ожидающих. Отмена одного ожидания не отменяет общую загрузку без явного правила владения. Разные ключи ограничены тремя активными трансферами.
- Проверить [Dart timeout](../lib/sources/soulseek_source.dart:322): отличать очередь пира и отсутствие прогресса; после timeout не оставлять вечную подписку и не создавать второго писателя.

### 5.6. Dart: источник, индекс и recovery

Файлы: [soulseek_source.dart](../lib/sources/soulseek_source.dart), [soulseek_platform_channel.dart](../lib/sources/soulseek_platform_channel.dart), [soulseek_models.dart](../lib/sources/soulseek_models.dart), [player_service.dart](../lib/core/player_service.dart:395), при необходимости [track_source.dart](../lib/sources/track_source.dart).

1. Выдавать путь только из подтверждённого native-кэша; исключить пустой и временный путь. Тяжёлую валидацию не дублировать на UI isolate.
2. В [`_waitForDownloadComplete()`](../lib/sources/soulseek_source.dart:322) фильтровать событие по ID/поколению до обновления индекса: сейчас внешний callback индексирует свой ключ при любом completion, хотя внутренний обработчик пути фильтрует ID. Ключ передавать явно, не выводить из префикса ID после dedupe.
3. Согласовать snapshot/event, чтобы мгновенное завершение между стартом и подпиской не терялось; невалидный completion не превращается в cache hit.
4. Recovery плеера сделать source-aware: Soulseek удаляет native-кэш и Dart-индекс по своему ключу, а не только [`YoutubeCache.evict()`](../lib/core/youtube_cache.dart:472). Не удалять другой кэш, не трактовать смену трека/ошибку обложки как битое аудио.
5. Один recovery на поколение воспроизведения: защититься от двух событий ошибки Media3 и смены трека пользователем. После бюджета — понятная ошибка и однократный skip по существующей политике.
6. Проверить физический источник пути и сохранить совместимость других источников и [офлайн-ветви](../lib/sources/soulseek_source.dart:412).

## 7. Отдельная задача SESSION-01, P3

Компоненты: [`Track.fromMap()`](../lib/models/track.dart:79), [playback_dao.dart](../lib/core/database/playback_dao.dart), [`_restoreSession()`](../lib/core/player_service.dart:716), [track_test.dart](../test/models/track_test.dart), [dao_test.dart](../test/database/dao_test.dart).

1. Получить обезличенную плохую запись/версию схемы. Стек указывает чтение ID установленной версии; текущий код также требует строковые источник/название/исполнителя. Установить конкретное поле и совместимость старой сериализации.
2. Идентичность не заменять пустым ID. Для старой схемы — миграция; для непригодной записи — контролируемый пропуск/карантин, сохраняя остальные треки. Defaults отображаемых полей определить отдельно.
3. После пропуска пересчитать текущий трек/индекс; проверить пустую очередь, позицию и отсутствие autoplay. Не стирать всю сессию из-за одной записи.
4. Unit-кейсы: отсутствующие/null/неверные типы, старый формат, смешанная очередь, round-trip, потребители в истории/плейлистах.

Готовность: пригодная часть очереди восстанавливается; исправление оформляется независимо от FLAC/Soulseek.

## 8. Необязательная задача MONO-01, P3

В [SoulseekWrapper.csproj](../soulseek-wrapper/SoulseekWrapper.csproj:3) рассмотреть [`<InvariantGlobalization>true</InvariantGlobalization>`](../soulseek-wrapper/SoulseekWrapper.csproj:3) только как эксперимент.

- Сначала проверить, что это штатный поиск локализованных ресурсов с fallback, а не потеря обязательных сборок. Не путать с телекоммуникационными satellite-сообщениями ОС.
- Подтвердить применение настройки к упакованному runtime: свойство библиотеки не обязательно управляет окружением конечного приложения. Исчезновение предупреждений не гарантировано.
- Риски: создание культур, сортировка/сравнение/регистр, разбор чисел/дат, тексты ошибок. Unicode и culture support — не одно и то же.
- Сравнить с настройкой/без неё при русской и английской локали: кириллические имена пиров/файлов, поиск, ключи кэша, логин, загрузка/resume, DNS/сокеты и сетевые ошибки, сериализация чисел.
- При косметической пользе или регрессии оставить настройку прежней; проверить упаковку ресурсов либо принять предупреждения. Не подавлять все Mono-логи.

## 9. Тестирование и команды будущего исполнителя

### Unit

## 10. Внедрение и порядок будущих коммитов

При подготовке плана ничего не коммитится. Порядок реализации:

1. FGS permission, failure-path, тесты и manifest verification. При срочном выпуске не объявлять FLAC исправленным.
2. Корреляционная диагностика и воспроизводимые негативные тесты pipeline.
3. .NET validation/atomic publication, расширение протокола, подтверждённая упаковка AAR.
4. Kotlin cache/state/retry, миграция/reconciliation, поколения и single-writer.
5. Dart индекс/source-aware recovery, общий бюджет, регрессия других источников.
6. Приёмочная device-диагностика; точечные UX-исправления только по воспроизведению.
7. Независимый SESSION-01.
8. MONO-01 только после полезного и безопасного эксперимента.

Промежуточные коммиты должны быть совместимы либо объединены в согласованный релиз .NET/Kotlin/Dart. Сначала ограниченная группа с upgrade существующих данных, затем расширение после приёмки. Миграции предпочтительно добавочные; старые записи не считать автоматически проверенными. Массовый сброс данных не является исправлением.

Откат: сохранить предыдущий подписанный артефакт и схему; откатывать согласованный набор слоёв, проверить обратную совместимость БД. Для Android предусмотреть rollback-релиз с новым versionCode, поскольку downgrade может быть запрещён. Не возвращать ошибочное разрешение/небезопасную публикацию: при блокирующей регрессии временно отключить Soulseek-загрузки с понятным сообщением. Невалидный кэш не восстанавливать как готовый.

## 11. Риски и открытые вопросы

- Текущая ревизия и установленный APK/AAR могут различаться; target SDK не равен API устройства.
- Ошибка FGS не доказывает завершение процесса: текущий catch продолжает работу. Требуются PID, timeline и состояние ОС.
- Нет доказательства, что FLAC испорчен транспортом/resume/гонкой, а не у пира; нужны файл, эталон и тесты.
- Глубина production-валидации и её стоимость не определены. Сигнатура не даёт гарантии полного декодирования.
- Не определена политика автологина/постоянного подключения и необходимость specialUse. Нельзя обещать бессрочную работу либо обход Android.
- Размер пира может устареть; равная длина не означает равное содержимое. Контракт счётчиков/offset нужно проверить.
- Atomic rename, durability и транзакция БД — разные гарантии. Обязательны reconciliation и тест реальной файловой системы/runtime.
- Очистка конфликтует с pin, писателями и читателями без координации; изменения DTO/БД/AAR требуют согласованного релиза.
- Для SESSION-01 необходима политика старого формата/непригодных ID, без коллизий пустых идентификаторов.
- Отсутствие ошибок обложек/множественного добавления не доказывает ни дефект, ни полную исправность — только необходимость сценарной проверки.
- Invariant globalization может изменить поведение и не убрать warnings; решение только по сравнению вариантов.

## 12. Не входит в первую итерацию

- Prebuffer и воспроизведение растущего частичного файла. Первая итерация — только полностью завершённый проверенный файл; существующий prefetch не равен prebuffer.
- Переписывание Soulseek-протокола, замена Soulseek.NET, миграция всех источников на новый кэш.
- Автоматическая подмена пира/версии трека без проверки идентичности.
- Редизайн обложек/множественного добавления без воспроизводимого дефекта.
- AOT/trimming и косметические Mono-оптимизации, не необходимые P0/P1.
- SESSION-01 не объединяется с Soulseek-патчем; MONO-01 необязателен.
- Обход Android через неверный тип FGS, снижение target SDK или бессрочные wake lock.
