## 2. Цели и анти-цели рефакторинга

### Цели (ЧТО достигаем)
1. **Архитектурная чистота** — убрать «божественные объекты», разведя файлы по понятным задачным единицам.
2. **Разделение слоёв** — явно отделить core (данные/сервисы/бизнес) от sources (источники контента) от UI; устранить смешение слоёв (UI-конверсия моделей, core-обработка UI-состояния).
3. **Платформозависимость управляемая** — вынести десктоп/Mobile-специфику за интерфейсы и DI, убрать разброс `if (isIOS||isAndroid)`.
4. **Тестируемость** — сделать unit-тесты возможными для desktop-виджетов, единообразить расположение тестов, не требовать живого доступа к сети для обычного прогона.
5. **Гигиена репозитория** — убрать «призрачные» вкладки из индексов, файлы-артефакты, чувствительные данные из корня.
6. **Прозрачность оценки** — каждый шаг имеет «галочку проверки» (прогон `dart test` / `flutter test analyze`).

### Анти-цели (ЧТО сознательно НЕ трогаем, чтобы не сломать)
1. **Поведение плеера** — не менять пользовательский поток: очереди, работает desktop/mobile так же, логика воспроизведения/постановки в очередь не меняется.
2. **Формат бэкапа/базы** — не менять схему SQLite `AppDatabase` и формат `PlaylistBackup`/миграции SharedPreferences→SQLite; рефакторинг — только внутренняя организация кода.
3. **Функциональность desktop и mobile** — оба пути `PlayerService`/`DesktopPlayerService` остаются рабочими.
4. **Контракты источников** — интерфейсы/track-source контракты НЕ меняются публично (см. §3 про `youtube_cache.dart`).
5. **Не переписывать алгоритмы** — только перестановка/разнесение; без изменения поведения.
6. **Не расширять функционал** — рефакторинг не добавляет новых возможностей.

## 3. Целевая архитектура

Принцип: **источники предложить изолировать от core-зависимостей**, но кэш **не** переносить в sources — остаёмся в core/ и импортируем оттуда.

### Целевая структура папок (после)

```
lib/
├── main.dart                     [факт] — точка входа; desktop-панель выносится, остаётся оркестрация
├── core/                         [факт]
│   ├── app_database.dart         [факт] — подлежит декомпозиции (см. Ф1)
│   ├── player_service.dart       [факт] — mobile; декомпозиция (Ф1)
│   ├── player_service_desktop.dart [факт] — desktop
│   ├── player_service_interface.dart [факт] — контракт не меняется
│   ├── repositories/             [новое] — вынести из core: history, playlist, backup, youtube_cache
│   │   ├── history_repository.dart       [перенос]
│   │   ├── playlist_repository.dart      [перенос]
│   │   └── ...
│   ├── platform/                 [новое] — вынести platform-зависимое (haptic, global_theme, image loader)
│   │   └── haptic_helper.dart            [перенос, desktop-ветка выносится]
│   └── ...
│
├── models/                       [факт] — track.dart, playlist.dart (без изменений)
│
├── sources/                      [факт]
│   ├── track_source.dart           [факт]
│   ├── source_registry.dart        [факт]
│   ├── muzmo_source.dart           [факт] — НЕ импортирует core кэш (см. Ф3)
│   ├── soundcloud_source.dart      [факт]
│   ├── youtube_source.dart         [факт]
│   ├── offline_audio_source.dart   [факт]
│   ├── artwork_provider.dart       [факт]
│   └── conversion/                [новое] — вырвать Media→model конверсии из UI/источников
│       └── track_media_convert.dart  [новое]
│
├── ui/
│   ├── pages/                    [факт] — player_page, search_page (декомпозиция)
│   ├── widgets/                  [факт] — общие (не platform): snack, back_button, artwork...
│   ├── desktop/                  [факт] — desktop-специфичные (shell, top_bar, player_bar, queue_panel)
│   └── platform/                 [ново] — если потребуется platform-специфичных виджетов
```

**ВАЖНО/Решение про youtube_cache:**
- **НЕ создавать `lib/sources/youtube_cache.dart`**, т.к. LRU-кэш жил и остаётся строго в `lib/core/youtube_cache.dart` [факт].
- Все импорты `package:player/sources/youtube_cache.dart` в выкладках/коде — убираем (сейчас отсутствие файла фактически ломает вкладку).
- `muzmo_source.dart`/`soundcloud_source.dart` импортируют кэш и НЕ должны его содержать; кэш остаётся общим в core/, источники только получают ссылку на кэш через конструктор (Ф3/DI).

**Решение про тесты:** институции в `test/` сделать такой же панелью, как код:

```
test/
├── unit/
│   ├── models/            [новое папки]
│   ├── core/
│   ├── repositories/
│   └── sources/            (уже есть)
├── integration/            [ново] — без live-маркеров
└── live/                   [ново] — пермяем из корня live-файлы с @Tags(['live'])
```

## 6. Риски и правила отката

### Правила отката (как минимизировать поломки)
1. **Бэкап-базы/Схемы НЕ трогаем.** Миграция SharedPreferences→SQLite и схема базы — вне правок. Любые изменения в benap` должны выверить бэк-тестами: `backup_test.dart`, `app_database_test.dart`, тесты на миграцию.
2. **live-тесты не трогаем** (@Tags(['live'])) — они проверяют реальный сетевой доступ; переносим бамптом, не меняя логику. Обычный прогон не должен их выполнять.
3. **СоГласен на интерфейс PlayerServiceInterface [факт]:** контракт не меняется в ближайшее время; тесты/сторона-выплата опираются на него.
4. **Каждый шаг — один коммит.** Исключение — циклические зависимости (невозможно разделить один файл на два без свободного сломанного состояния); тогда «серые коммиты» с закрытыми временными мостями разрешены только если они идут в той же серии и проходят `flutter test` вернут.
5. **Прогон `flutter analyze`** — обязателен перед каждым коммитом; анализ не тюнинг, а барьер входа: если он ломается, рефи́ refactoring откатывается до последнего зелёного состояния (гит).
6. **Тест-консистенция**: перед Ф1, Ф2 и Ф3 — фиксируем текущий зелёный снапшот тестов (базельная линия), чтобы видеть регрессию. Снять baseline: прогнать `flutter test` / `flutter analyze` и сохранить результат.
7. **Для «призрачных» вкладок 0.1** — это не реффи, а закрытие VS-ного интерфейса; обратный шаг — повторное открыть файл с диска (он сейчас отсутствует). Риск минимальный.
8. **Рolстоо` хардлов`:** для desktop widget-тестов — widget-тесты частично не исполняются в headless (`flutter test` по widget_reshape); на это тоже обратить внимание: в «обычные прогон» они не должны быть «медь», завязанные на дисплей.

### Таблица рисков и митигаций
| Риск | Митигация |
|---|---|
| Сломана схема базы/бэкап | Не менять миграции; базовые тесты; baseline regress test |
| Сломанный loop воспроизведения при декомпозиции PlayerService | Изменять только структуру, не логику; smoke-тест player |

| Личный секрет в корне | Залить в `.gitignore`; не коммиить |
| Рассинхрон открытых вкладок | Закрыть без сохранения; не стремиться пересоздать отсутствующие файлы |

## 7. Оценка объёмов и рекомендация по атомарности

### Оценки относительных объёмов (приблизительные)
- **Ф0 (гигиена):** малый объём, 4 подшага, безопасный, быстрый. 
- **Ф1 (монолиты):** 8 под-шагов, каждый по 1–3нг. раза — самое ёмкое по изменению (объём «божеств»).
- **Ф2 (слои):** 3–6 под-шагов, пересекается с Ф1.
- **Ф3 (платформа+DI):** 6 под-шагов; 3.5 (DI) — самая рискован-tuning (большой объём правок вызовов).
- **Ф4 (тесты):** 4 под-шага; добавление покрытия после стабилизации структуры.

### Рекомендация по атомарности
- **Один логический шаг = один коммит** со своим `flutter analyze` (черновиком).
- Для крупных монолитов разбить на под-C-шаги (например: 1.1a «выделить модели запросов», 1.1b «выделить миграции», 1.1c «репозиторий»), даже если некоторые из них — сожжённые — это позволит изолировать риски.
- Циклические зависимости (разъединение очереди/послуги) — сделать step-unbreakable pair.
- **Не смешивать в одном коммите гигиену и рефакторинг**, т.к. гигиена — безопасна и не влияет на структуру во время прогона тестов; это упрощает откат.

### Галочка для каждого шага (единый критерий приёмки)
```
☐ `flutter analyze` — без ошибок
☐ `flutter test` — зелёный (обычный прогон, без @tags live)
☐ (если применимо) live-прогон (@Tags(['live'])) — sources не сломаны
☐ Проверка «призрачных» импортов не появилась (поиск имен фантом-файлов)
☐ Ручной запус desktop и mobile (smoke) — если изменялся main.dart / desktop / player
```
